Start

Zero-difference GNSS processing

This handbook describes how to start a ZDGNSS run, follow it through the Bernese Processing Engine (BPE), and inspect the results. It covers the controllers, processing stages and utilities used by this GPSUSER.

Where to begin

  • Run a session with the quick start. Use software and setup to prepare a GPSUSER.
  • Follow a processing stage in the processing architecture. The wrapper reference shows the PCF behind each listed stage.
  • Investigate a run using monitoring and recovery, then quality checks and plots.
  • Find supporting tools in the toolbox and maintenance reference.

How a run is launched

The Python controller schedules Perl wrappers. Each wrapper starts a specific PCF. The PCF defines the BPE jobs and their dependencies. You can also run an individual wrapper or start a BPE directly from the Bernese menu.

Quick start

Start the wizard

Run the following command from a terminal on the processing host.

python3 /storage/homefs/ck18y530/ZDGNSS_RUN/zdgnss_wizard.py &

Follow the prompts in the wizard. If you are preparing a new GPSUSER, see Software and setup for the required processing components.

Before starting a custom sequence

If you want to select or reorder individual processing jobs, open the Python run controller. For a first run with that controller, use Dry-Run to review the generated commands, campaign and session selection before choosing START BPE.

Follow the run

Use Monitoring and recovery to check job status and locate logs. See Quality checks and plots when the run has produced its outputs.

Software and setup

Prepare the GPSUSER

Use Copy PCF in the toolbox to copy the PCF and its SCRIPT and OPT components into your GPSUSER. The tool checks for conflicts before copying.

Check the processing dependencies

Perl

The scripts ZD_CODSPP_E, ZD_MRKOB__E and ZD_STDPRE use RetryHelper.pm from ~/ZDGNSS_RUN/perl. See Monitoring and recovery for the retry functions and usage.

Python

If you need to modify a Python helper, make a copy first. Update its path in the corresponding script. The documented entry points are STATION_SELECTION, CHECK_SAT_CLOCKS, ZD_HELMR1_VS, plotCOMPAR and plotORBVER.

MATLAB

For local changes, copy the MATLAB helpers and update their paths in ZD_CMP_LAPACK and ZD_STATION_SELECTION where applicable.

Project-specific Bernese programs

This GPSUSER uses the project versions PHACOR_CK, ADDNEQ2_LAPACK and GPSEST_CLOCK_GRID.

System Overview

Processing architecture

From campaign to PCF

  1. Python controller. Choose the campaign, partition and sessions, then arrange the jobs you want to run. See Python run controller.
  2. Perl wrappers. Each wrapper launches one PCF. Use the wrapper reference to identify the corresponding workflow or start a stage from the command line.
  3. Bernese BPE. Follow the selected PCF to see its jobs, dependencies, scripts and options. The PCF page shows the process table and any WAIT dependencies.

How to read the workflow

  • Prepare the run. The wrapper reference starts with preparation and preprocessing, then lists code and phase screening.
  • Follow the solution stages. It lists the FA, AR, IA, finish, 3D and PPP steps together with their PCFs.
  • Find final and clock stages. Final IA, finish and 3D each have a separate wrapper. Clock densification has its own wrapper as well.

The wrapper list is a reference for locating each stage. To see the job sequence for a particular run, inspect Dry-Run in the Python controller. To see dependencies within one PCF, open its process table.

Inspect the results

Use the processing statistics for an overview of the run, validation or comparison plots for the corresponding solution checks, and campaign exclusions for station or satellite diagnostics. The quality checks page points to the tools and inputs for each task.

Controllers

Python run controller

The controller start_bpe_gui.py is available in /storage/homefs/ck18y530/perl/ZDGNSS. It starts the selected Perl wrappers in the order shown in the job list.

Configure a run

  1. Choose the campaign and partition.
  2. Set the first session and the number of sessions.
  3. Add the required jobs and use the up and down controls to set their order.
  4. Give the output log a name if you want to keep a run log. Use the wait condition when the launch of jobs must be spaced out.
  5. Choose Dry-Run to display the commands. Review them before choosing START BPE.

Run a single stage

Use the matching Perl wrapper directly when you only need one step. Its -h option gives the arguments for that wrapper.

Perl wrappers and PCFs

Each wrapper launches the PCF listed below. Run the wrapper with -h for its available options. PCF names link to the generated PCF reference when that file is present in the selected GPSUSER.

Preparation and screening

  • preparation.pl runs ZDGNSS_PREPARATION.PCF.
  • preprocessing.pl runs ZDGNSS_PREPROCESSING.PCF.
  • codescreening.pl runs ZDGNSS_CODESCREENING.PCF.
  • phasescreening.pl runs ZDGNSS_PHASESCREENING.PCF.

Solution stages

  • fa.pl runs ZDGNSS_SOL_FA.PCF.
  • ar.pl runs ZDGNSS_AR.PCF.
  • ia.pl runs ZDGNSS_SOL_IA.PCF.
  • finish.pl runs ZDGNSS_FINISH.PCF.
  • 3d.pl runs ZDGNSS_3D.PCF.
  • ppp.pl runs ZDGNSS_PPP.PCF.

Final processing and clock densification

  • ia_final.pl runs ZDGNSS_SOL_FINAL.PCF.
  • finish_final.pl runs ZDGNSS_FINISH_FINAL.PCF.
  • 3d_final.pl runs ZDGNSS_3D_FINAL.PCF.
  • clkden.pl runs ZDGNSS_CLKDEN.PCF.

Process a day relative to today

The wrappers support -lw=R with an offset R. The command below runs preparation for campaign CK_ZDGNSS for the day three days before the current day.

~/perl/preparation.pl -lw=R -camp=CK_ZDGNSS R=3

Operations and Tools

Toolbox and maintenance

Open the Python toolbox from the project tools directory.

cd ~/ZDGNSS_RUN/Tools
python3 Tools.py

Prepare or inspect a GPSUSER

  • Copy PCF (get_my_pcf). Copy a PCF and its SCRIPT and OPT components between GPSUSERs, including across accounts. The tool checks for conflicts to prevent overwrites.
  • PCF Viewer (pcf_viewer). Select a PCF and then a job row to see its input file and script. Select a PCF variable to highlight its uses in those files. Use the Locked button before editing the script. PID notes are saved as PCFFILENAME_help.json in the PCF directory.
  • Find variables in BPE (find_variables_in_bpe). Search PCFs for a variable such as $(FIN).
  • Search file in BPE (search_file_in_bpe). Look for a file pattern across PCFs. Example search strings are $(FIN)_$YSS+0 and $(FIN)_$YSS+0.STD.
  • Filetracer (filetracer). Experimental tool for tracing file accesses and modifications by scripts.

Clean up after a test

  • Clean GPSUSER (clean_gpsuser). Identify unused option directories and scripts. Start with analysis to review the results. The cleanup mode moves unused items.
  • Clean subfolders (clean_subfolders). Clean a campaign when reusing it for a test.
  • Clean residuals (clean_residuals.py). Use after a one-day test with normal file deletion disabled. It deletes the files that DEL_RES_1D would have deleted. The tool is in /storage/homefs/ck18y530/python. Use python3 clean_residuals.py -h to see an example invocation.

Monitoring and recovery

Check a running BPE

  • Monitor BPE (monitor_bpe). Open the campaign monitor from the toolbox. It works like tkbpe and can monitor different campaigns.
  • error_watch. Monitor .RUN files and send status messages via Telegram. Set up your own notifications using error_watch_manual.txt before starting error_watch.sh. The configuration also uses IGNORE.LIST and WATCH.LIST. Copying an existing installation with its notification settings can send alerts to the previous recipient.

Record a BPE jump

JumpLogger.pm records jumps in a log file. Copy it from ck18y530/GPSUSER/SCRIPT into your SCRIPT directory and set the log path in the module. Add the following import near the start of the script after @ISA.

use lib "$ENV{HOME}/GPSUSER/SCRIPT";
use JumpLogger qw(logJump);

Call logJump immediately before the existing prtGoto call.

logJump($bpe, $param2);
prtGoto(\$bpe, $param2);

The module also provides jumpAndLog. The original notes leave its current behaviour unverified.

Retry a Bernese program

RetryHelper.pm is in ~/ZDGNSS_RUN/perl. The module provides run_with_retry, run_with_retry_noerror and run_retry_goto. This example shows how to retry SATMRK.

use lib "$ENV{HOME}/ZDGNSS_RUN/perl";
use RetryHelper qw(run_with_retry);

my $PGMNAM = "SATMRK";
run_with_retry($bpe, $PGMNAM, 10);

The setup notes list the scripts that use this module. CODSPP_E uses run_with_retry_noerror. The retry log path can be adjusted in the module.

Quality checks and plots

Choose a plot

The following plotting scripts are documented in /storage/homefs/ck18y530/python.

  • Processing statistics. generate_processing_plots.py provides a GUI for plotting run statistics from PROCESSING_$YD+0 files.
  • Solution validation. generate_validation_plots.py plots results from VALIDATE_SOLUTION.PCF.
  • Solution comparison. generate_comparison_plots.py plots results from CMPSOL.PCF.
  • Repeatability differences. plot_repeatabilites_differences.py compares two solutions using results from VALIDATE_SOLUTION.PCF. The filename uses the spelling shown here.

Investigate exclusions

  • Satellites. satellite_problems_plot.py analyses reasons for satellite exclusions. Give it the campaign’s MSC directory. By default, it writes its outputs to the current working directory.
  • Stations. The station-exclusion notes list Plot_excluded_stations.py and give the following invocation under the filename summarize_excluded_stations.py. Check the filename in your installation. The input is the campaign’s MSC directory.
python3 ~/python/summarize_excluded_stations.py "$R/CK_ZDGNSS/MSC"

Helpers called by the processing chain

  • Clock completeness. check_clk_completeness is used by CHECK_SAT_CLOCKS.
  • Stations used for validation. extract_fix_stations is used by HELMR1_VS in VALIDATE_SOLUTION.PCF. It extracts stations with flag W or I from a .CRD file.
