Start

Zero-difference GNSS processing

This handbook describes how to start a ZDGNSS run, follow it through the Bernese Processing Engine (BPE), and inspect the results. It covers the controllers, processing stages and utilities used by this GPSUSER.

Where to begin

  • Run a session with the quick start. Use software and setup to prepare a GPSUSER.
  • Follow a processing stage in the processing architecture. Use the PCF guide for the jobs and the wrapper reference for the launchers.
  • Set up a run or check the daily chain using the ZDGNSS run package and scheduled runs guides.
  • Investigate a run using monitoring and recovery, then quality checks and plots.
  • Find supporting tools in the toolbox and maintenance reference or the Python utility index.

How a run is launched

The Python controller schedules Perl wrappers. Each wrapper starts a specific PCF. The PCF defines the BPE jobs and their dependencies. You can also run an individual wrapper or start a BPE directly from the Bernese menu.

System Overview

Processing architecture

From campaign to PCF

  1. Python controller. Choose the campaign, partition and sessions, then arrange the jobs you want to run. See Python run controller.
  2. Perl wrappers. Each wrapper launches one PCF. Use the wrapper reference to identify the corresponding workflow or start a stage from the command line.
  3. Bernese BPE. Follow the selected PCF to see its jobs, dependencies, scripts and options. The PCF page shows the process table and any WAIT dependencies.

How to read the workflow

  • Prepare the run. The wrapper reference starts with preparation and preprocessing, then lists code and phase screening.
  • Follow the solution stages. It lists the FA, AR, IA, finish, 3D and PPP steps together with their PCFs.
  • Find final and clock stages. Final IA, finish and 3D each have a separate wrapper. Clock densification has its own wrapper as well.

The wrapper list is a reference for locating each stage. To see the job sequence for a particular run, inspect Dry-Run in the Python controller. To see dependencies within one PCF, open its process table.

Inspect the results

Use the processing statistics for an overview of the run, validation or comparison plots for the corresponding solution checks, and campaign exclusions for station or satellite diagnostics. The quality checks page points to the tools and inputs for each task.

ZDGNSS PCF guide

This guide covers the 18 ZDGNSS_*.PCF files in ~/GPSUSER/PCF on Sedna. Open a PCF link to inspect its job PIDs, scripts, option directories and WAIT dependencies. Several workflows also use ZD_STATUS to wait for or write a stage flag. Check the PCF variables for the expected flag and configuration when diagnosing a hand-off.

Prepare and screen observations

  • ZDGNSS_PREPARATION.PCF checks the campaign, copies observations and reference files, selects the station network, prepares a priori coordinates and orbits, and screens station and satellite availability.
  • ZDGNSS_PREPROCESSING.PCF runs initial observation preprocessing, computes code weights and performs station-wise satellite-clock checks.
  • ZDGNSS_CODESCREENING.PCF generates code-based orbits and code residuals, checks stations, marks bad observations, extracts OSBs and produces code-only clocks.
  • ZDGNSS_PHASESCREENING.PCF preprocesses phase data and iterates residual screening. It checks stations and observations, adjusts thresholds and weights, and combines clocks.

Estimate the solution and resolve ambiguities

  • ZDGNSS_SOL_FA.PCF sets up and combines normal equations, with optional LEO NEQs. It checks the datum, supports a large-system or pre-eliminated-clock path and produces clocks, orbits and statistics. It selects the FA configuration.
  • ZDGNSS_AR.PCF estimates wide-lane and narrow-lane biases and ambiguities. It checks bias estimates, updates the orbit and combined bias file, and records resolved ambiguities in observation files.
  • ZDGNSS_SOL_IA.PCF uses the same job structure as the FA solution with the IA configuration.
  • ZDGNSS_SOL_FINAL.PCF uses that solution structure with the FINAL configuration.
  • ZDGNSS_PPP.PCF prepares inputs and clocks, screens and solves PPP station by station, merges OSB and coordinate files, and writes a processing summary.
  • ZDGNSS_LEONEQ.PCF selects and checks LEO data, prepares and executes parallel LEO NEQ jobs, and checks that the NEQs exist. The solution PCFs have a separate job to add LEO NEQs when required.

Finish, combine three-day arcs and densify clocks

  • ZDGNSS_FINISH.PCF creates final PRE orbits, satellite attitude information and processing summaries. It can compare full and pre-eliminated-clock solutions. It waits for IA and writes FINISH_R.
  • ZDGNSS_FINISH_FINAL.PCF performs the same finishing stages with the FINAL configuration. It waits for IA_F and writes FINISH_F.
  • ZDGNSS_3D.PCF prepares three-day inputs, generates the long-arc solution using the LAPACK ADDNEQ2 jobs, creates orbit and clock products, and saves results. It selects the 3D configuration.
  • ZDGNSS_3D_FINAL.PCF uses the same three-day job structure with the 3DF configuration.
  • ZDGNSS_CLKDEN.PCF prepares receiver clocks and troposphere estimates, merges and combines clock products, changes the clock reference, and produces high-rate clocks and a satellite-only clock product.
  • ZDGNSS_CLKDEN_FINAL.PCF uses the same densification structure with the CLKDENF configuration. The other variant selects CLKDEN.

Validate and compare

  • ZDGNSS_VALSOL.PCF prepares solution data for coordinate repeatability and Helmert checks, orbit verification, and station and satellite diagnostics. Its final jobs generate plots and concatenate validation output.
  • ZDGNSS_CMPSOL.PCF prepares solution data, compares ERP, orbit and clock products, runs COMPAR2 and a Helmert comparison, and combines their summaries.

Use the Perl wrapper reference to find the entry point for a stage and Quality checks and plots to choose a diagnostic after the run.

ADDNEQ2 with LAPACK

The project build in ~/ADDNEQ2_LAPACK stacks Bernese normal equations (NEQs) and solves the combined system. The executable on Sedna is EXE_IFC/ADDNEQ2. The ZDGNSS three-day workflows have dedicated ZD_ADDNEQ2_LA_P and ZD_ADDNEQ2_LA_E jobs. The solution and finish workflows also have a LAPACK-related processing path. See the PCF guide to locate these jobs.

How it solves the system

ADDNEQ2.f90 drives the stacking and calls the solver. NEQSOLVE.f90 copies the normal matrix into full storage and uses LAPACK DPOTRF for Cholesky factorisation, DPOTRS for the solution vector and DPOTRI for the inverse. It copies the inverse back into the normal-equation representation for subsequent use. PARELIMI.f90 is also part of the project build.

Build and diagnose

  • FOR/compile_addneq2.sh expects Intel ifort and the Bernese library and module directories. It links Intel MKL and the Bernese IFC library and writes EXE_IFC/ADDNEQ2.
  • The source names under FOR are links into FOR/BERN. The top-level folder also contains source copies. Identify the source location used by the build script before comparing versions.
  • compile.txt records older commands using an ADDNEQ2_LAPACK2 path. Use the project build script as the reference for the current directory layout.
  • In the program print file, check the DPOTRF, DPOTRS and DPOTRI return codes and the inversion timing. A zero LAPACK return code indicates success for that operation. If the solve fails, check the preceding NEQ assembly and datum checks in the corresponding PCF.

GPSEST satellite-clock grid

The project build in ~/GPSEST_CLOCK_GRID can restrict satellite-clock parameter creation to an epoch grid. It uses the parameter epoch, reference epoch and tolerance to decide whether a clock parameter is on the grid. The grid option controls parameter creation during estimation.

Input settings

Set the clock-grid options in the project FOR/GPSEST.INP template or the corresponding input panel.

  • CLKS_GRID enables the feature. The template defaults to 0.
  • CLKS_GRID_STEP sets the interval in seconds. The default is 300.
  • CLKS_GRID_REF sets the reference MJD in the same time scale as the parameter epochs. The default 0 aligns a 300-second grid with midnight.
  • CLKS_GRID_TOL sets the epoch tolerance in seconds. The default is 0.001. It must be positive and smaller than half the interval.
  • CLKS_GRID_LOG prints the created clock epochs and clocks passed to NEQ saving when enabled.

With the grid enabled, the implementation requires satellite-clock estimation (CLOCKS = 1), PRE24 = NO and OPTELI(24) = 0 after option checking. The print file reports the interval, reference MJD and tolerance. Use these lines and the optional clock log to confirm which settings the run applied.

Sources and build

FOR/GPSCLOCKGRID.f90 contains the grid test, epoch counting and option validation. FOR/compile_gpsest_grid.sh compiles the clock-grid module and the affected GPSEST routines plus the main program using ifort. It writes EXE_IFC/GPSEST. The folder also contains EXE_GNU/GPSEST. Check the actual executable and input panel selected by your run when comparing results.

See the PCF guide for the separate clock-densification workflows and the Python utilities for post-run clock-completeness checks.

PHACOR phase correction

The project build in ~/PHACOR_CK reads GPSEST narrow-lane bias (NLB) logs and estimates satellite clock and orbit corrections from zero-difference ambiguities. Its program name is PHACOR and the executable present on Sedna is EXE_GNU/PHACOR.

Inputs and estimation

  1. The executable reads its Bernese input file. Configure the GPSEST logs through LOGFILES. The program reads the constants file, station coordinates and orbit data for the geometry.
  2. It builds an ambiguity grid, forms between-satellite observation intervals and clusters them. It can estimate jump parameters when configured to check phase jumps.
  3. It solves a weighted system separately for each selected GNSS constellation. It uses datum and orbit constraints, then derives residuals, satellite quality statistics and corrections.

Outputs and checks

When all selected systems solve successfully, the program writes corrected BIA, OSB, CLK and PRE orbit products to the BIAFILE_MOD, OSBFILE_MOD, CLKFILE_MOD and ORBITFILE_MOD destinations. It requires each of these output names to be set. The program report includes the inputs, processing trace and statistics. With debug enabled, DEBUG_OUT selects the detailed trace file.

Start with the report if a product is missing. The main program records conditions such as no selected NLB logs, a constellation with no usable observation intervals and a failed solution. These conditions help identify whether to inspect the input selection, the observations or the solve.

FOR/PHACOR.f90 contains the processing driver. FOR/D_PHACOR.f90 contains the supporting modules. OBJ_GNU/Makefile provides the GNU build configuration.

Operations and Tools

Toolbox and maintenance

The toolbox is a tabbed PyQt5 launcher. The standalone copy is in ~/Tools. A second copy is bundled with the ZDGNSS run package under ~/ZDGNSS_RUN/Tools. To open the standalone copy, run the launcher from its directory.

cd ~/Tools

Both copies have application code in programs/ and individual help pages in help/. The bundled copy also has the PCF File History tab described below.

Prepare or inspect a GPSUSER

  • Copy PCF (get_my_pcf). Select one or more PCFs and the source and destination GPSUSER. The tool builds a copy plan for the PCFs, their SCRIPT and OPT dependencies and CFG files referenced by V_PCFCONFIG. It deduplicates shared dependencies, flags missing sources and blocks destination conflicts before copying.
  • PCF Viewer (pcf_viewer). Select a PCF and then a job row to see its input file and script. Select a PCF variable to highlight its uses in those files. Use the Locked button before editing the script. PID notes are saved as <PCF_NAME>_help.json in the PCF directory.
  • Find variables in BPE (find_variables_in_bpe). Search for a case-sensitive string such as $(FIN) in the INP files belonging to OPT directories referenced by the PCFs. The results identify each PCF, matching files and shared OPT directories.
  • Search file in BPE (search_file_in_bpe). Search INP values for a pattern, look up the extension in MENU_EXT.INP when applicable and identify PCFs using the matching option directory. Example search strings are $(FIN)_$YSS+0 and $(FIN)_$YSS+0.STD.
  • File Tracer (filetracer). Statically trace file accesses and modifications in Bernese Perl scripts. It groups detected patterns and helps locate reads, writes, moves and deletions.
  • PCF File History. In the bundled toolbox, select a filename or template and one or more PCFs. The tool shows potential readers and writers by PID and follows known WAIT dependencies. Dynamic paths and runtime branches can leave gaps in this static view.

Monitoring and recovery

Check a running BPE

  • Monitor BPE (monitor_bpe). Open the campaign monitor from the toolbox. It works like tkbpe and can monitor different campaigns.
  • error_watch. Use the monitor below for Telegram alerts from selected logs.

Send log alerts with error_watch

~/error_watch/error_watch.sh scans the files listed in WATCH.LIST for error and messages of the form Session <number>: finished. It also sends a warning when a watched file is missing. Each matching alert can include the file and the matched log line.

Files and modes
  • WATCH.LIST takes one absolute log path per line, typically a campaign .RUN file. Blank lines and lines starting with # are skipped.
  • IGNORE.LIST takes /absolute/path/to/log|substring. The path must match the watched file, and the installed script compares the substring literally and case-sensitively. The scan for error and session patterns itself is case-insensitive.
  • MODE=NEW is the default. error_watch.STATE records reported path and line-number pairs to suppress repeated alerts for those lines. A replaced or rotated log can reuse line numbers, so account for the state file when troubleshooting missing alerts.
  • MODE=A reports matching lines on each scan and bypasses the recorded-line check.
Prepare a scheduled check

Start from the directory containing WATCH.LIST, IGNORE.LIST and error_watch.STATE. The script resolves these names relative to its working directory, so set that directory explicitly if you schedule the check. Use error_watch_manual.txt for the Telegram setup and configure your own recipient before running it. Telegram receives matched log lines, so watch files whose contents are suitable for that notification channel.

Record a BPE jump

JumpLogger.pm records jumps in a log file. Copy it from ck18y530/GPSUSER/SCRIPT into your SCRIPT directory and set the log path in the module. Add the following import near the start of the script after @ISA.

use lib "$ENV{HOME}/GPSUSER/SCRIPT";
use JumpLogger qw(logJump);

Call logJump immediately before the existing prtGoto call.

logJump($bpe, $param2);
prtGoto(\$bpe, $param2);

The module also provides jumpAndLog. The original notes leave its current behaviour unverified.

Retry a Bernese program

RetryHelper.pm is in ~/ZDGNSS_RUN/perl. The module provides run_with_retry, run_with_retry_noerror and run_retry_goto. This example shows how to retry SATMRK.

use lib "$ENV{HOME}/ZDGNSS_RUN/perl";
use RetryHelper qw(run_with_retry);

my $PGMNAM = "SATMRK";
run_with_retry($bpe, $PGMNAM, 10);

The setup notes list the scripts that use this module. CODSPP_E uses run_with_retry_noerror. The retry log path can be adjusted in the module.

Scheduled ZDGNSS runs

The active wrappers in ~/bash_scripts/ZDGNSS prepare the Bernese environment and launch processes in the background. They set BPE, AUTO and EXE and redirect output to log files. The older per-stage cron wrappers are in GRAVEYARD/.

Daily processing chain

run_zdgnss.sh calls ~/perl/ZDGNSS/bpe_worker_routine.py with master_config.json. It writes a top-level log named bpe_workerYYDDD.log under ~/perl/ZDGNSS/LOGR. The worker builds an ordered list of enabled jobs. Each job's days_ago is applied to the reference date, and n sets its session count. A real run creates a timestamped directory under the configured log_base with bpe_launcher.log and the individual job logs.

The worker treats a nonzero exit code or an error match in a job log as a failure. It normally stops at the first failed job. continue_after_error controls whether to continue, and global_wait sets the delay between jobs.

Use the worker's --dry-run option to check the resulting commands without launching jobs or creating run logs. Use a Python environment compatible with the routine worker.

cd ~/perl/ZDGNSS
python3 bpe_worker_routine.py --config master_config.json --dry-run

--date changes the reference day, --days-ago and --n override job session settings, and --jobs selects wrapper filenames while preserving configuration order.

Validation and comparison wrappers

  • run_zd_cmpsol_mgex_1day_rapid_cron.sh calls cmpsol_mgex.pl with -R=5 for the MGEX comparison and writes CMPSOL_MGX_1DAY_RAPIDYYDDD.log. The offset in the actual command is five days.

Both validation and comparison wrappers use the launch date in the log suffix. When checking a specific session, use the invoked wrapper's offset and the session reported in the logs.

Bernese BPE Documentation

~/Bernese_BPE_Documentation on Sedna builds the website for the configured Bernese GPSUSERs. It combines a generated reference for PCFs, scripts and option files with the manually written Handbook. Use the ZDGNSS PCF guide to navigate the processing stages and their generated references.

Project files

  • update_manual.py reads the PCF/, SCRIPT/ and OPT/ directories of each configured GPSUSER and generates the manual.
  • update_manual_gui.py lets you manage GPSUSERs, edit Handbook entries and comments, build the manual and publish it.
  • manual_sources.txt lists the source GPSUSER directories. manual_config.json sets the output directory, source list and optional handbook_order for each GPSUSER.
  • manual_additions/handbooks/<gpsuser-slug>/ contains the Markdown pages. For this Handbook the slug is ck18y530-gpsuser. The sibling comments/ and history/ directories contain manual comments and change records.
  • site/ is the generated output on Sedna. site/index.html is the overall GPSUSER overview. With multiple GPSUSERs, each manual is under site/sources/<gpsuser-slug>/.
  • publish_manual.sh commits and pushes the built version. .github/workflows/deploy-pages.yml deploys site/ to GitHub Pages.

Edit and build

Save Handbook changes under the selected GPSUSER's Handbook folder. Use handbook_order in manual_config.json to place articles in reading order. Its paths are relative to that GPSUSER's Handbook folder.

Open the GUI from the project directory.

cd ~/Bernese_BPE_Documentation
python3 update_manual_gui.py
  • Only rebuild the manual rebuilds all configured GPSUSER manuals. Use this after changing the builder or a shared setting.
  • Update GPSUSER rebuilds the selected GPSUSER and refreshes the common overview. The builder also refreshes any other branches that lack compatible protected downloads for the supplied password.
  • Only publish to GitHub uses the existing site/ output. Choose it after checking the local build.

For a local review, clear Push site/ to GitHub after a successful build before starting the build.

Preview and check downloads

Run a local web server from the project directory and open http://localhost:8000/. If the browser is on another computer, use an SSH tunnel to the server on Sedna.

python3 -m http.server 8000 --bind 127.0.0.1 --directory site

The build takes the shared download password from the GUI or from DOCBUILDER_DOWNLOAD_PASSWORD. For each GPSUSER, test a representative download with an incorrect password and then with the intended password. The HTML documentation and Handbook text are visible to anyone who can access the Pages site. The password protects the downloaded source files.

Publish a reviewed build

Check git status --short from the project directory before using Only publish to GitHub. The publish script uses git add -A, so it includes pending changes across the checkout.

The script checks for site/index.html, rejects old source_files directories and requires the downloads/.protected marker for each generated manual. It then pushes the commit to origin/main. In GitHub, check that Deploy manual site succeeded for that commit and open the deployed site to confirm the changes.
